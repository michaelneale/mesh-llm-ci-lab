# Releasing mesh-llm

One workflow builds, tests and publishes a release:
`.github/workflows/binaries.yml`. [ci/ci.md](ci/ci.md) lists the platforms it
builds and what is checked on each.

## Cut a release

From a clean local `main` that matches `origin/main`:

```bash
just release 0.81.0        # or 0.81.0-rc.1
```

It asks for confirmation, starts the workflow on `main`, watches it, and checks
the published release. The Actions page does the same: run **Release binaries**
on `main` with the version and **publish** ticked.

To build and test every archive without publishing anything:

```bash
just release 0.81.0 --canary
```

The workflow, in order:

1. On each platform, sets the version in the source
   (`scripts/release-version.sh`), builds, packages, and starts the packaged
   binary where the runner can run it.
2. When every platform has succeeded, writes `native-runtimes.json`.
3. Commits the version change to `main` as `v0.81.0: prepare release source`,
   tags that commit and pushes both.
4. Creates the GitHub release with every archive and its checksum attached.
   The notes are generated by GitHub and start at the last stable release.
5. For a stable version, tells `Mesh-LLM/mesh-packaging` to build the packages,
   container images and npm release. This needs the
   `MESH_AGENT_IMAGES_DISPATCH_TOKEN` secret and is skipped without it.

A version with a suffix, such as `v0.81.0-rc.1`, is published as a prerelease,
is not marked latest, and does not start mesh-packaging.

Nothing is tagged or published unless every platform succeeds. After a failed
build, fix the cause and release the same version again. If the last job fails
after it pushed the tag, delete the tag before running it again.

When `main` rejects pushes from the workflow, set the version in a pull request
first (`scripts/release-version.sh v0.81.0`), merge it, then release. The
workflow then has no version change to commit and tags `main` as it is.

Do not create a release from GitHub's **Draft a new release** form: it attaches
no archives.

## Signing keys

Packaging signs the `mesh-llm` executable and checks the signature when these
repository secrets are set. Without them the binary is published unsigned.

- `MESH_RELEASE_ATTESTATION_SIGNING_KEY_FILE`
- `MESH_RELEASE_ATTESTATION_PUBLIC_KEY_FILE`

Each secret holds the full JSON contents of a key file, not a path. Generate a
key pair with:

```bash
umask 077
mkdir -p /tmp/mesh-release-attestation
cargo run -q -p xtask -- release-attestation generate-keypair \
  --private-key-out /tmp/mesh-release-attestation/mesh-release-attestation-private-key.json \
  --public-key-out /tmp/mesh-release-attestation/mesh-release-attestation-public-key.json
```

Store the key pair in 1Password before adding or rotating the secrets. The
production pair is in the `mesh-llm` vault as
`GitHub Actions Release Attestation Signing Keys`, with fields named after the
secrets. Set the secrets from the files:

```bash
gh secret set MESH_RELEASE_ATTESTATION_SIGNING_KEY_FILE --app actions \
  < /tmp/mesh-release-attestation/mesh-release-attestation-private-key.json
gh secret set MESH_RELEASE_ATTESTATION_PUBLIC_KEY_FILE --app actions \
  < /tmp/mesh-release-attestation/mesh-release-attestation-public-key.json
```

## Check a published release

Download an archive and its `.sha256`, check the checksum, unpack it, and
inspect the signature:

```bash
cargo run -p xtask -- release-attestation inspect \
  --binary /tmp/test-bundle/mesh-llm \
  --public-key-file /tmp/mesh-release-attestation/mesh-release-attestation-public-key.json \
  --json
```

`valid` means the binary matches the release signer. `missing` means it was
published unsigned. `invalid` means the bytes changed after packaging, or no
public key was given for a signed binary.

Then start it and send one chat request, as `ci/simple/smoke.sh` does. The CUDA
and ROCm archives are never started by the workflow, so check those on a
machine with the card.

## Analytics key

Release binaries report anonymous usage only when `MESH_LLM_POSTHOG_KEY` is set
at compile time. The workflow passes it from the repository secret of that
name, and `scripts/build-host.sh` prints whether a key was present, never the
key. A build without the secret reports nothing unless `MESH_LLM_POSTHOG_KEY`
is set when the binary runs. Forks build without the secret.
`mesh/website/src/docs/pages/analytics.md` describes what is collected and how
to turn it off.

## Build a release archive locally

```bash
just release-build
just release-bundle v0.81.0
```

For a GPU flavour, use its build recipe and name the flavour when packaging:

```bash
just release-build-cuda
just release-bundle v0.81.0 dist cuda
```

A MeshLLM archive contains `mesh-llm`, `host-imports.json`,
`product-manifest.json` and one `native-runtimes/<runtime-id>` directory.
Windows archives are `.zip` files for `x86_64-pc-windows-msvc`.

## Not done by this workflow

- Publishing the Rust crates to crates.io.
- Building `MeshLLMFFI.xcframework.zip` and updating `Package.swift` for
  SwiftPM.
- Committing the built console into the Node, Swift and Kotlin SDK directories
  of the tagged source.
